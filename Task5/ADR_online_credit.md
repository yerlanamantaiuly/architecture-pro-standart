|**№**|**Требование**|

| 1 | Новый online-процесс подачи кредитной заявки не должен строиться на прямом обращении интернет-банка к API или БД АБС. |
| 2 | Для соблюдения SLA по онлайн-заявкам цифровые каналы должны передавать заявку в кредитный конвейер напрямую через управляемый интеграционный контур, а не ждать суточного обмена из АБС. |
| 3 | Для сайта и интернет-банка требуется защищенная передача чувствительных данных, маскирование ПДн в логах и фиксация согласия на обработку данных. |
| 4 | Онлайн-сервисы должны работать 24/7, поддерживать целевую доступность 99,9% и учитывать работу резервного ЦОД. |
| 5 | Пользовательские операции должны иметь быстрый отклик; решение должно поддерживать горизонтальное масштабирование хотя бы на уровне онлайн-контура, кредитного конвейера и скоринга. |

| 7 | Реализацию SMS-подтверждения и SMS-уведомлений желательно выполнить без доработки ядра платформы интернет-банка подрядчика. |
| 8 | Решение должно быть совместимо с существующими платформами банка и по возможности использовать технологии, по которым уже есть внутренняя экспертиза. |
| 9 | Необходимо обеспечить идемпотентность подачи заявки, сквозной идентификатор между каналами и аудит изменения статусов. |

### **Решение**
Диаграммы приложены отдельными файлами:

- `context-online-credit.drawio`
- `components-online-credit.drawio`

Для кредитного online-процесса предлагается ввести отдельный `API онлайн-кредитования`, который станет точкой входа для сайта и интернет-банка и будет оркестрировать взаимодействие с кредитным конвейером, скорингом, SMS и статусами заявок. Это позволяет не использовать АБС как online-backend для цифровых каналов и убрать зависимость от суточного обмена `АБС -> Кредитный конвейер` для новых цифровых заявок.

Основные элементы решения:
- `Сайт` как публичный канал подачи кредитной заявки;
- `Интернет-банк` как канал для действующих клиентов и предодобренных предложений;
- `API онлайн-кредитования` как новый интеграционный слой банка;
- `Кредитный конвейер` как основная система бизнес-процесса заявки;
- `Система кредитного скоринга` как сервис принятия скорингового решения;
- `Бюро кредитных историй` как внешний источник данных для новых клиентов;
- `Сервис SMS-подтверждения` и `СМС-шлюз` для подтверждения действий и уведомлений;
- `АБС` как система отделений и учетный контур, но не как точка online-подачи.

Логика решения:
- сайт и интернет-банк отправляют заявки в `API онлайн-кредитования`;
- API валидирует данные, присваивает идентификатор заявки, обеспечивает идемпотентность и запускает процесс в `Кредитном конвейере`;
- для сценария сайта с паспортными данными API инициирует скоринговый сценарий через конвейер и скоринг, используя БКИ как основной внешний источник данных;
- для интернет-банка поддерживается сценарий работы с предодобренными предложениями и повторным упрощенным скорингом;
- если клиент приходит в отделение, сотрудник продолжает ту же заявку через связку `АБС + API онлайн-кредитования + Кредитный конвейер`;
- статусы заявки и уведомления клиенту формируются из конвейера и передаются через SMS-контур.

Такой подход позволяет:
- выполнить требование по более быстрому online-пути без ожидания ночной интеграции из АБС;
- сохранить кредитный конвейер как основной бизнес-процессовый контур;
- разгрузить АБС и не строить новый клиентский канал вокруг legacy-системы;
- поддержать предодобренные предложения, повторный скоринг и продолжение заявки в отделении;
- оставить архитектурный задел для развития кредитного цифрового канала без полного переписывания интернет-банка.

### **Альтернативы**
1. Оставить подачу online-заявок только через АБС с последующей суточной передачей в кредитный конвейер.
Минусы: не выполняется ожидание по скорости обработки и сценарию предодобренной заявки в тот же рабочий день.

2. Сделать прямую интеграцию интернет-банка с АБС для кредитных заявок.
Минусы: противоречит ограничениям FURPS+, усиливает нагрузку на АБС и привязывает новый кредитный online-процесс к перегруженной legacy-системе.

3. Выполнять массовые фоновые перерасчеты скоринга для всех клиентов ради предодобренных предложений.
Минусы: противоречит ограничению по нагрузке на систему скоринга в рабочие часы и создает высокий инфраструктурный риск.

4. Создать отдельный изолированный online-кредитный процесс без использования кредитного конвейера.
Минусы: приведет к дублированию бизнес-логики и правил принятия решения, усложнит сопровождение и увеличит риск рассинхронизации с основным кредитным процессом банка.

**Недостатки, ограничения, риски**

- Для нового клиента с сайта предварительное решение ограничено качеством данных БКИ и не может заменить полноценную идентификацию в отделении.
- Появляется новый интеграционный слой `API онлайн-кредитования`, который становится критичной точкой для цифровых каналов и требует отказоустойчивости, аудита и мониторинга.
- При плохой реализации сквозной идентификации возможны дубли заявок между сайтом, интернет-банком, отделением и кредитным конвейером.
- Суточный обмен между АБС и кредитным конвейером остается ограничением для части legacy-сценариев, поэтому нужно четко определить, какой контур является источником истины для online-заявки.
- Система скоринга остается чувствительной к нагрузке; при маркетинговых кампаниях может потребоваться отдельное управление лимитами, очередями и правилами вызова.
- Требования доступности 99,9% и работы резервного ЦОД для интернет-банка и нового online-контура могут быть достигнуты только поэтапно, так как текущая инфраструктура банка к ним пока не полностью готова.
